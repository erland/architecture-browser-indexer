# Platform integration contract for source viewing

## Purpose

This document defines the platform-facing contract that allows the platform component to retrieve source code for a selected indexed object without persisting full source text inside platform snapshots.

The contract is intentionally split into two phases:

1. **run-time handoff** from the worker run endpoint to the platform, where the worker returns retained-source access metadata that the platform can persist alongside the imported snapshot context
2. **on-demand source retrieval** from the source-read endpoint, where the platform sends the retained-source handle together with a repository-relative file path and optional line-range hints

The contract is read-only. It is not a generic file-browser API.

## Integration goals

The platform integration must satisfy the following rules:

- the platform must not store full source files in its core snapshot model
- the platform must not send absolute filesystem paths back to the indexer
- the platform must only send the retained-source handle returned by the worker and a repository-relative path already known from indexed `sourceRefs`
- the worker must resolve files only inside the retained source root associated with the handle
- the worker may refuse reads for expired, invalid, missing, oversized, binary, or out-of-root files

## Stable worker contracts

### 1. Run endpoint handoff

The existing worker run endpoint remains the primary source of source-access metadata:

- **Endpoint**: `POST /api/index-jobs/run`
- **Response type**: `HttpWorkerRunResponse`
- **Platform-facing field**: `sourceAccess`

`HttpWorkerRunResponse.sourceAccess` is the stable handoff object that the platform must persist for later source reads.

#### `sourceAccess` shape

The current typed DTO is `HttpWorkerSourceAccess`.

The platform must treat the following fields as the stable integration surface:

- `sourceHandle`: opaque retained-source identifier generated by the worker
- `sourceType`: source retention mode, currently aligned with local-path or retained-git-root behavior
- `retainedUntil`: optional timestamp describing when the worker expects the retained source root to expire
- `sourceRootKind`: descriptive root kind for diagnostics and future policy handling

### Platform persistence rule

For each imported snapshot that should support source viewing, the platform should persist at minimum:

- snapshot identifier or imported snapshot reference in platform
- worker base URL / worker connection identity already associated with the source tree
- `sourceHandle` from `sourceAccess`
- optional `retainedUntil`
- enough contextual metadata to determine whether source viewing should still be offered in the UI

The platform must treat `sourceHandle` as opaque. It must not attempt to derive paths, TTLs, or storage semantics from its content.

## 2. On-demand source read contract

The source-read endpoint is the worker API used after the platform has a retained-source handle.

- **Endpoint**: `POST /api/source-files/read`
- **Request type**: `HttpWorkerSourceFileReadRequest`
- **Response type**: `HttpWorkerSourceFileReadResponse`

### Request rules

The platform must send:

- `sourceHandle`: the opaque handle returned earlier by the run endpoint
- `path`: repository-relative file path, normally taken from an indexed `SourceRef.path`
- optional `requestedStartLine`
- optional `requestedEndLine`

The platform must **not** send:

- absolute paths
- synthetic paths not present in indexed source references unless it is intentionally reading another indexed file through a supported UI path
- traversal segments such as `..`

### Request example

```json
{
  "sourceHandle": "srch_01JY...",
  "path": "apps/api/src/main/java/com/example/MyResource.java",
  "requestedStartLine": 42,
  "requestedEndLine": 80
}
```

### Response semantics

The worker currently returns:

- `sourceHandle`
- `path`
- `language`
- `totalLineCount`
- `fileSizeBytes`
- `requestedStartLine`
- `requestedEndLine`
- `sourceText`

The platform should interpret these fields as follows.

#### `language`

A viewer-friendly language identifier for syntax highlighting. Examples include:

- `java`
- `typescript`
- `tsx`
- `javascript`
- `json`
- `xml`
- `yaml`
- `sql`
- `markdown`
- `plaintext`

The platform should use `language` when present. If `language` is `null`, the platform may fall back to extension-based highlighting or plain text.

#### `requestedStartLine` / `requestedEndLine`

These are echoed hints, not currently a server-side content slice. The response still contains the full file text. The platform should use these values to:

- scroll the viewer to the relevant location
- optionally apply a highlighted line band in the UI

#### `sourceText`

The full returned text of the resolved source file, encoded as JSON string content.

### Response example

```json
{
  "sourceHandle": "srch_01JY...",
  "path": "apps/api/src/main/java/com/example/MyResource.java",
  "language": "java",
  "totalLineCount": 210,
  "fileSizeBytes": 8451,
  "requestedStartLine": 42,
  "requestedEndLine": 80,
  "sourceText": "package com.example;\n..."
}
```

## Error handling contract

The platform must treat source viewing as a best-effort capability.

The worker may reject a read when:

- the handle is unknown
- the handle is expired
- the retained root no longer exists
- the path is invalid or escapes the retained root
- the file is not a regular text file
- the file exceeds the configured size limit

### Platform behavior on failure

When a source read fails, the platform should:

- show a non-destructive error message in the source viewer area
- keep the user in the current browser session
- allow retry if appropriate
- avoid removing snapshot data or browser state

Recommended user-facing error categories:

- **Source no longer available** for expired or missing retained roots
- **File could not be opened safely** for invalid path or policy failures
- **File is not viewable as text** for binary or unsupported file cases

The platform should not surface raw worker filesystem details to the user.

## Path and source-reference expectations

The source-view feature depends on indexed `SourceRef.path` values being repository-relative and stable within the retained source root.

The platform integration should therefore follow this flow:

1. user selects an entity, relationship, or diagnostic in platform
2. platform reads one or more indexed `sourceRefs`
3. platform chooses a source ref to open
4. platform sends `sourceHandle + sourceRef.path + optional line hints`
5. worker resolves the file relative to the retained root for that handle

### Selection rule for the first platform version

For the first non-clickable source viewer implementation, the platform should use a simple priority rule:

1. first source ref with non-empty `path`
2. prefer one that also has `startLine` and `endLine`
3. if multiple source refs exist, expose them in a simple chooser or open the first one deterministically

## Retention expectations

Retained source is not guaranteed indefinitely.

Current worker behavior:

- local-path source handles generally reference an existing local root and do not require a copied retained checkout
- git-based temp workspaces are retained under the worker source-retention area
- retained git roots are subject to TTL-based cleanup
- source reads update `lastAccessedAt` on successful use
- cleanup may run on worker startup, before runs, and before source reads

### Platform implications

The platform should assume that:

- a previously valid `sourceHandle` can later expire
- source viewing availability may differ across snapshots depending on worker retention policy
- source-view UI should degrade gracefully when retention has elapsed

The platform should not attempt to extend retention by itself. The worker remains the source of truth for retention lifecycle.

## Security boundary

The worker-side source API is intentionally narrower than a repository browser.

The platform must preserve that boundary by only sending:

- worker-issued `sourceHandle`
- repository-relative file paths already known through indexed metadata
- optional line hints

The platform must not offer arbitrary path entry for end users in the first version.

## Recommended platform-side data model additions

A minimal platform persistence shape for the first version could include:

- `sourceHandle`
- `retainedUntil`
- `workerBaseUrl` or worker connection identifier
- `sourceType`
- `sourceRootKind`

A minimal source-view request assembled by platform could include:

- `sourceHandle`
- `path`
- `requestedStartLine`
- `requestedEndLine`

## Backward-compatibility notes

The platform must tolerate these scenarios:

- `sourceAccess` absent on older worker versions
- `language` absent or `null`
- `retainedUntil` absent
- future additive fields appearing in both DTOs

Recommended rule:

- treat missing optional fields as unsupported capability or reduced viewer friendliness, not as fatal contract errors

## Recommended first platform UX using this contract

1. show an **Open source** action for a selected object only when both of these exist:
   - a usable `sourceRef.path`
   - snapshot-linked `sourceHandle`
2. call platform backend, which proxies the worker source-read request
3. render source text in a read-only viewer with syntax highlighting
4. scroll to `requestedStartLine`
5. optionally highlight `requestedStartLine..requestedEndLine`
6. if the worker returns an error, show a friendly unavailable message

## Contract summary

For the first source-view implementation, the platform integration contract is:

- get `sourceAccess` from `POST /api/index-jobs/run`
- persist the opaque `sourceHandle`
- later call `POST /api/source-files/read` with:
  - `sourceHandle`
  - repository-relative `path`
  - optional line hints
- render the returned `sourceText` using the provided `language`
- gracefully handle retention expiry and safe-read rejections

This keeps the platform snapshot lean while allowing on-demand source viewing with a stable worker-owned retention model.
